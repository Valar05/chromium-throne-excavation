# Vlad Excavation

## 1. Placement

Vlad is part of the Fortress browser-and-phone automation organism. Vlad belongs primarily to the **phone-local context, synchronization, and review plane**. Vlad was neither the Chromium Throne extension nor the Android tap/swipe body.

A correct decomposition is:

- Phone Hands transports and dispatches phone work.
- The Android bridge and Termux execute phone work.
- The overlay governs visible screen authority.
- Atom exposes phone-local status and command/context access.
- **Vlad keeps Judgment Jar context synchronized and available to Atom/campaign/review paths.**
- Venice and other reviewers contribute planning, continuation, or verdict material.

## 2. Recovered daemon shape

Source evidence described `vlad_swarm_daemon.py` as the long-running daemon and `setup_vlad_swarm_daemon.sh` as its setup/service wrapper. The wrapper established a phone-local state directory, logs, a service receipt, and a recorded source hash. The daemon invoked the Vlad/Jar synchronization path on heartbeat and was described as the only watcher for that fast-access lane.

An installer path for “Atom + Vlad phone” chained the Atom phone setup with Vlad daemon setup, probed Atom’s loopback status endpoint, and emitted an installation receipt. Another Atom install path treated Judgment Jar configuration and Vlad setup as prerequisites and arranged a boot-time Atom/Vlad presence check.

No daemon, installer, service unit, or configuration is copied into this graveyard.

## 3. Judgment Jar fast access

The recovered fast-access document described a typed context-and-receipt system:

- Atom could obtain context receipts from synchronized Judgment Jar material.
- Venice planning/completion outputs could be imported as typed `review_verdict` material.
- Runtime and receipted workers used the fast path rather than ad hoc full-corpus scans.
- Vlad’s daemon heartbeat drove `vlad-jars sync`.
- Atom distinguished locally captured work from Home Center delivery, including states equivalent to captured and pending delivery.

That last distinction is critical: local capture was not falsely labeled cloud delivery.

## 4. Data and receipt model

| Artifact | What it could prove | What it could not prove alone |
|---|---|---|
| Vlad process/heartbeat | Daemon was alive at an observation point | Jars were current or a requested action completed |
| Source hash receipt | Installed daemon source corresponded to a recorded hash | Service was running correctly |
| Jar sync result | A synchronization attempt/result occurred | Every consumer used the new context |
| Atom status response | Atom local endpoint responded | Home Center received pending work |
| Context receipt | A worker received bounded judgment context | Worker executed the external task |
| Review verdict | A reviewer produced typed output | Human acceptance or device-side success |
| Pending Home Center state | Local result awaited delivery | Cloud delivery completed |

## 5. Vlad in the phone campaign

The recovered phone campaign explicitly probed Vlad’s process and service receipt against the canonical runtime, attempted repair/restart when necessary, and included Vlad in the review gate set. This is strong evidence that Vlad was a required subsystem in the campaign’s definition of phone readiness.

It is not evidence that Vlad controlled the phone’s screen. Vlad’s role was to keep the judgment/context nervous system coherent and to participate in review readiness.

## 6. Vlad and overlay self-healing

Search evidence connected Vlad setup and tests to overlay recovery/self-healing paths. The safe interpretation is that Vlad participated in the broader retained-context and recovery organism around the phone, not that Vlad directly owned Android overlay state. The overlay remained governed by its native package, content-provider state, control gate, and relay integration.

## 7. Vlad, Venice, and Atom

| System | Primary recovered concern |
|---|---|
| Atom | Phone-local command/status/context aperture and captured/pending receipts |
| Vlad | Continuous Judgment Jar synchronization, fast context, service receipt, review gate |
| Venice | Planning/continuation/completion review material in browser and campaign paths |

The names frequently appear together because they formed a cognitive/review layer around execution. They must still be diagnosed separately. A Venice verdict cannot prove a Vlad sync; a Vlad heartbeat cannot prove Atom delivery; an Atom capture cannot prove Home Center receipt.

## 8. Failure model

Vlad-related failure classes include:

- daemon absent or stale;
- service receipt missing or mismatched to source/runtime;
- Jar configuration absent;
- sync heartbeat failing;
- Atom endpoint unavailable despite Vlad presence;
- context captured but not delivered;
- review verdict missing, malformed, or not imported;
- campaign gate failing even when process-level probes pass.

The appropriate archaeological status for each is “unknown” unless a contemporaneous receipt proves it. Recovery code is evidence of intended handling, not of successful recovery.

## 9. Current-status warning

No fresh Vlad PID, heartbeat, Jar sync, Atom endpoint, context receipt, Home Center delivery, or review-gate canary was executed for this documentation. The graveyard records source-level and historical operational evidence only.

## 10. Disposition

Vlad should be remembered as the persistent phone-side keeper of synchronized judgment context and review readiness. Vlad made the automation organism more than a set of blind remote-control commands, but surviving evidence does not justify claiming that Vlad or the whole organism reached stable accepted operation.
